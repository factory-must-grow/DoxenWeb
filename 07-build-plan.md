# 07 — План работ

Восемь этапов. Каждый заканчивается работающим состоянием, которое
можно запустить и проверить. **Не начинать следующий, пока критерии
текущего не выполнены.**

Порядок выбран так, чтобы самая рискованная часть (движок `.docx`)
была сделана и покрыта тестами раньше, чем на неё начнёт опираться веб.

---

## Этап 1. Каркас и база

Подключить ASP.NET Core Identity на EF Core + Npgsql и самописные
миграции для бизнес-таблиц — два механизма с непересекающимися
таблицами, см. `01-architecture.md`. Порядок при старте: сначала
`context.Database.MigrateAsync()`, потом `Migrations.ApplyAsync()`.

Первая самописная миграция создаёт `plans`, `user_profiles`,
`usage_counters`, `generation_log` и начальный тариф `free`.

Реализовать создание первого администратора при старте, если в системе
нет ни одного пользователя в роли `Admin`: почта и пароль из переменных
`DOXEN_ADMIN_EMAIL` и `DOXEN_ADMIN_PASSWORD`, создание — через
`UserManager`, роль — через `RoleManager`. Если переменные не заданы —
не создавать и написать предупреждение в лог.

**Готово, когда:** приложение стартует на чистой базе, создаёт таблицы
обоих механизмов, заводит администратора; повторный старт не ломается
и не дублирует данные.

---

## Этап 2. Движок: разбор

`Doxen.Engine.TemplateParser` по спецификации `03-engine.md`.
Вместе с ним — проект тестов и тесты 1–5, 9 из списка в конце
`03-engine.md`.

Тестовые `.docx` собирать программно в коде теста через OpenXml —
в том числе с намеренно разорванной на несколько `<w:t>` переменной.
Не класть бинарные файлы в репозиторий.

**Готово, когда:** все перечисленные тесты зелёные, включая разорванную
переменную и переменную в колонтитуле.

---

## Этап 3. Движок: разрешение и генерация

`ValueResolver`, `PersonFormatter`, `TemplateGenerator`, `GenerateBatch`
и `AnswersFile` по спецификациям `03-engine.md` и `04-answers-file.md`.
Тесты 6–13.

**Готово, когда:** есть тест полного цикла — шаблон плюс JSON на входе,
корректный `.docx` на выходе, `SubstitutionCount` совпадает с ожидаемым.
Пакет из трёх наборов даёт три разных документа. Проверить результат,
открыв файл в Word или LibreOffice вручную хотя бы один раз: тесты не
поймают повреждённую разметку, которую Word откажется открывать.

---

## Этап 4. Аутентификация

Регистрация, вход, выход, смена пароля, страница профиля —
через `UserManager`/`SignInManager`. Настройка Identity и то, что
осталось за нами (cookie, anti-forgery, HTTPS), — по `01-architecture.md`.

При регистрации в одной операции создаётся и учётная запись Identity,
и строка `user_profiles` с тарифом `free`. Если второе не удалось —
откатить первое, иначе появится пользователь без профиля и все
запросы к тарифу по нему упадут.

**Готово, когда:** можно зарегистрироваться, выйти, войти снова.
И отдельно проверено вручную:
- после смены пароля сессия в другом браузере перестаёт работать
  (проверка `SecurityStampValidator` — включён ли `ValidationInterval`);
- после 5 неверных паролей вход блокируется на 15 минут;
- `/admin` недоступна пользователю без роли `Admin`;
- у нового пользователя есть строка в `user_profiles` с тарифом `free`.

## Этап 5. Основной сценарий

Главная с демо-разбором, экран `/generate`, форма, генерация,
скачивание документа и файла ответов. Хранение загруженного шаблона
в `IMemoryCache` по `01-architecture.md`. Предпросмотр справа — в конце
этапа, он наименее критичен.

Здесь же — сохранение состояния формы при регистрации анонима
(см. `05-screens.md`), это легко упустить.

Пакетный режим — тоже здесь, после того как одиночный сценарий
заработал целиком: разделение на «общее» и таблицу «по документам»
по `05-screens.md`, вставка диапазона из Excel в таблицу, выдача ZIP.

Контроль занятой памяти с двумя порогами и ожиданием для бесплатных
пользователей (`01-architecture.md`) — в конце этапа, когда основной
путь уже работает.

**Готово, когда:** сквозной сценарий работает целиком — загрузил
шаблон, заполнил, скачал документ и файл ответов; загрузил тот же
шаблон вместе с файлом ответов — поля подставились, спрашивается
только недостающее; файл ответов с тремя наборами даёт ZIP из трёх
документов; в таблицу пакета вставляется диапазон из Excel.

Отдельно проверить: после перезапуска приложения открытая страница
заполнения сообщает «Загрузка шаблона устарела, выберите файл ещё раз»
и не теряет введённые значения — кеш в памяти переживать перезапуск
не обязан, но пользователь не должен видеть исключение.

## Этап 6. Лимиты и учёт

`LimitChecker`, счётчики, три проверки в порядке из `05-screens.md`,
инкремент атомарным upsert'ом, запись в `generation_log`.

Плюс проверка `allow_batch` и подсчёт пакета целиком по
`05-screens.md`.

**Готово, когда:** при временном занижении лимитов в админке до
единицы каждая из трёх проверок срабатывает с правильным текстом;
счётчик растёт только при успешной генерации; при ошибке генерации
документ не списывается; пакет из трёх наборов увеличивает счётчик
на три, а пакет, где один набор упал, — на два.

## Этап 8. Отделка

Применить дизайн-систему по `06-design-system.md` ко всем экранам,
привести в порядок тексты ошибок и пустых состояний, проверить

Отдельно проверить на мобильном: главная и экран заполнения должны

под форму.

**Готово, когда:** пройден чек-лист доступности из `06-design-system.md`,
на мобильном нет горизонтальной прокрутки, все тексты ошибок
соответствуют разделу «Тон сообщений».

## Что вне рамок этой работы

Не реализовывать без отдельной постановки:

- приём платежей и подписки (заказчик подключит после запуска)
- **циклы внутри одного документа** — вывод списка в таблицу через
  `{{#each}}`. Это не то же самое, что пакетная генерация, которая в
  плане есть; подробнее в `03-engine.md`, раздел «Чего движок
  намеренно не умеет»
- другие форматы файла ответов кроме JSON
- восстановление пароля по почте (нужен почтовый сервис — обсудить
  отдельно)

Если по ходу работы кажется, что нужно **записать пользовательский
файл на диск** или завести под него таблицу — это признак неверно
понятой задачи, см. `00-README.md` и `01-architecture.md`.
