# Doxen Web — комплект технических заданий

Веб-версия десктопного приложения Doxen: генерация документов `.docx`
по шаблонам с переменными `{{path.to.value}}`, без Microsoft Office.

Домен: **doxen.ru**

## Как пользоваться этим комплектом

Документы читаются в порядке нумерации. Первые пять — справочные
(архитектура, БД, движок, формат файла ответов, экраны), последний —
пошаговый план работ с критериями приёмки.

| Файл | Что внутри |
|---|---|
| `01-architecture.md` | Стек, структура решения, ключевые архитектурные решения и почему они такие |
| `02-database.md` | Схема PostgreSQL, миграции, правила доступа к данным без ORM |
| `03-engine.md` | Движок разбора и генерации `.docx` — самая ответственная часть |
| `04-answers-file.md` | Формат файла ответов (JSON) |
| `05-screens.md` | Экраны, маршруты, пользовательские сценарии |
| `06-design-system.md` | Дизайн-токены, переопределения Bootstrap, правила вёрстки |
| `07-build-plan.md` | Этапы работ с критериями готовности |

Рядом лежит `doxen-design.html` — утверждённый макет дизайна.
Это эталон: цвета, шрифты, отступы и тон текстов берутся оттуда,
а не придумываются заново.

## Главное, что нужно понять до начала

**1. Пользовательские файлы никогда не пишутся на диск.** Загруженный
шаблон живёт в оперативной памяти (`IMemoryCache`, 2 часа) между шагами
заполнения; готовый документ отдаётся сразу и нигде не сохраняется;
файл ответов формируется на лету. Причина не только в приватности как
принципе: доверенности и заявления содержат паспортные данные, и запись
их на диск — даже временная — превращает обработку персональных данных
в их хранение со всеми обязанностями по 152-ФЗ.

В БД хранятся: пользователи, тарифы, счётчики использования, журнал
операций. В журнале — только количества и результат, **без имён файлов
и без значений переменных**.

Любое решение, которое требует записать пользовательский файл на диск,
неверно — см. `01-architecture.md`.

**2. Веб-версия проще десктопной, а не сложнее.** В десктопе структура
данных описывалась тремя таблицами (типы сущностей, поля, значения), и
поэтому существовал мастер создания недостающих полей. В вебе структуру
задаёт сам JSON-файл ответов: вложенность объекта — это и есть связи.
Поэтому в веб-версии **нет** понятий «тип сущности», «поле-ссылка»,
«конфликт вида поля» и всего мастера схемы. Остаётся ровно одна проблема:
«по этому пути нет значения» — спросить у пользователя.

**3. Учёт использования считается в документах, но защищён потолком
сложности шаблона.** Причина: лимит «N документов» обходится склейкой
тысячи доверенностей в один файл. Поэтому у каждого тарифа три числа —
документов в месяц, максимум переменных в шаблоне, максимум размера
файла. Все три настраиваются в админке.

**4. Две оси генерации, из них реализуется одна.** Документы получаются
перемножением осей «для кого» (наборы данных — десять контрагентов) и
«что именно» (шаблоны — договор, акт, доверенность). Сейчас делается
только первая: шаблон загружается один, наборов может быть много,
на выходе ZIP. Формат файла ответов уже готов ко второй оси, поэтому
файлы, сохранённые сейчас, не придётся переделывать. Подробности в
`04-answers-file.md`.

Не путать это с **циклами внутри одного документа** — таблицей, которая
повторяется по элементам списка на одном листе. Это третья, отдельная
задача, и она сейчас не делается; см. `03-engine.md`.

**5. Аутентификация — ASP.NET Core Identity, EF Core только под неё.**
Требование «без ORM» относится к бизнес-данным: тарифы, счётчики,
журнал и выборки для админки пишутся чистым Npgsql. EF Core обслуживает
исключительно собственные таблицы Identity, EF-запросов писать не
нужно вообще. Обоснование и границы — в `01-architecture.md`.
